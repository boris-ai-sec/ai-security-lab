## 1. Question, claim boundary and prohibited shortcuts

**Question:** When a controlled underlying tool definition changes *after a synthetic approval* while the ARC bundle, task, action and G1 binding remain unchanged, which layer notices the change, which layer prevents the consequential request, and what effect is **independently persisted** in the Demo ERP?

The comparison is intentionally three-plane:

1. **ARC G1** establishes declared-subject/binding consistency, **not** execution authorization. A G1 `PASS` is expected to miss underlying-definition-only drift by design and shall retain `execution_authorized: false` in the evidence.
2. **Mock Guardian + an actual enforcing Gateway** establish a decision and whether it was honored **before a real outbound ERP POST**. The research `reconciling` mock is not silently equivalent to a production ACS/AGT Guardian or a standard feature of the Gateway.
3. **Demo ERP/PostgreSQL read-only observer** reports actual durable rows and quantities, including after HTTP errors or lost acknowledgements. A mock harness ledger, runtime `ALLOW` or gateway response is not an independent ERP observation.

This is an isolated, fictional authority/ERP test. It is **not** a production integration, ACS conformance certification, official AIMM validation, general MCP-client security proof, universal bypass-resistance assessment, or inference about unchanged-definition behavior drift (T9). The synthetic tests inform possible maturity-evidence design only; they do not amend normative §5.1.

## 4. Paolo's R1 provenance boundary, acquisition owner and claim scope

**Normative source mode:** `definition_source` is the single field used at A1, R1, in the out-of-band envelope and in the verifier. Allowed vocabulary: `contract_fixture_current`, `fresh_tools_list`, `cached_approved_copy`. Current C0–C3 uses only **`contract_fixture_current`**. It signifies a trusted controlled fixture read, not a live MCP freshness guarantee.

**Selected acquisition architecture for this pilot (review candidate):**

1. **A1:** the trusted isolated fixture controller exposes the active exact D0 Tool object with its stable `source_identifier` and active `source_revision`. The **Gateway itself** obtains the object, records its original bytes, creates an immutable in-operation snapshot, JCS-canonicalizes and hashes it, and records A1 `definition_source` plus the D0 digest. The synthetic approval/admission binds D0, declared quantity 40 and its Q=40 reservation to the logical operation.
2. **Mutation:** for C2/C3 only, the trusted fixture controller activates D1 after A1 and holds that exact D1 stable through the end of the case. C0 remains D0 throughout; C1 has no definition mutation and must not fabricate a suppressed R1. The ARC declaration, binding, logical request, grant and `operation_id` do not change in C2/C3. The source records a monotonic activation sequence/revision, without attesting real remote-server execution.
3. **R1:** immediately before a possible outbound ERP POST, the **Gateway** obtains **D0 for C0, D1 for C2/C3** from that controlled source, records original bytes/revision and an immutable measured snapshot, computes the §3 hash, and presents digest/provenance through the test-only out-of-band `control/presentBasis` channel bound to run/operation and a fresh R1 attempt. That same snapshot determines **40×1=40 for C0** or the **40×3=120 candidate for C2/C3**. C2 must withhold the candidate forward when HELD. C1 records suppression/not-reached stages without invented R1 activity.
4. **Last-mile binding:** the Gateway retains the immutable measured object and converts from it on the authorized forward path; it must not silently refetch a different definition after R1 or use mutable independently supplied conversion settings. If the lab's actual downstream executor can interpret a different active revision, the Gateway must lock/pin its execution revision or compare before the last cancellable point and fail closed on change; otherwise the remaining TOCTOU window must be declared and the narrow `contract_fixture_current` claim must not be inflated into server-side behavior assurance.
5. **Trust/evidence:** before freeze, name the source endpoint/path, allowed caller identities, acquisition/authentication mechanism, revision/sequence, byte capture, integrity protection and failure disposition. If the Gateway cannot obtain a trustworthy current snapshot, there is no valid R1 forward permit. A separately named *fixture collector* cannot be the decision-time measurement owner for this architecture.

**Canonical C2 limitation (Paolo):** §9, under *Mandatory C2 claim boundary*, is the **single normative text**. Do not maintain a second, slightly different quotation here. Every C2 report, final summary and machine-readable export must use the §9 wording exactly. A pointer/reference here is not a substitute for including that exact text in the output required by §9.

A future `fresh_tools_list` experiment would additionally require authenticated and authorization-equivalent retrieval from the target MCP server, identity, selected Tool object, protocol version, cache/notification handling, freshness limits, raw requests/responses, and binding to the subsequent invocation. A server may still change its behavior between retrieval and execution. `list_changed` by itself is not client-refresh proof.

A `cached_approved_copy` experiment would test the separate stale-D0 versus active-D1 problem. Paolo's eight-client observations are contextual external research, not measurements reproduced by T4.

**Explicit exclusions:** MCP `fresh_tools_list` and cached-copy/T4b experiments; a real server changing execution behavior while Tool digest stays constant (T9); production ACS/AGT conformance; T8/late partial-effect and multi-tenant cases. Malachi's reference test P4 illustrates T4b but is **not** a fifth C0–C3 pilot scenario. All new modes require a separate reviewed revision; do not silently widen this pilot.

**Decision mapping for this pilot, subject to matching actual lab implementation:**

| Guardian wire reply / condition | Pilot interpretation | Physical Gateway behavior |
|---|---|---|
| Valid `allow`, `r1_permit`, matching current request/operation/attempt identity | Candidate forward permit **only at R1**, not A1 | Continue only if all independent local checks pass and same-snapshot binding holds |
| `ask` + `basis_reauth_required`, `ask_details.timeout_disposition:"deny"` | `HELD` (documented test-only mapping) | Withhold ERP POST; preserve held state and evidence; no auto reapproval |
| Valid `deny` | Denied | Withhold ERP POST |
| `defer`, `modify`, unsupported decision, missing/invalid basis, malformed reply, stale/replayed attempt, wrong request ID, mismatch in source/provenance | No valid permit | Fail closed, withhold ERP POST, classify distinct error/reason |
| Guardian transport failure, timeout, lost or ambiguous R1 acknowledgement | No valid permit | Fail closed **before** forward; do not guess authorization |

The Gateway must verify exact ACS schema, decision stage, `request_id` correlation and authenticated binding to `run_id`, `operation_id` and `attempt_id`; another request's `allow` is never usable. **Malachi's proposed F2 parameters (not yet approved for this exact version or implemented):** Gateway measures and authenticates the basis; Guardian verifies it. The isolated orchestrator generates a cryptographically random **32-byte per-run key**, mounted **read-only into Gateway and Guardian only**, never in environment variables, published evidence or logs; `key_id = run_id`; destroy the key after run closure. Use **HMAC-SHA256 over RFC 8785 JCS of the complete envelope excluding its `signature` field**. All §3 provenance fields, `capture_stage`, case/run/operation/attempt, source identity/revision, audience, `issued_at`, nonce, algorithm/schema/version and key identity are covered; §7 defines the proposed design and pending exact schema decisions. Guardian durably records accepted `(run_id, attempt_id)` to reject replay; **maximum basis age is 30 seconds**. Authentication, freshness, audience, source or identity mismatch yields **`basis_not_presented`**, and Gateway does not send. Replay and permit reuse retain distinct diagnostics (§9). A shared HMAC establishes integrity within this two-party trust boundary; Gateway **and Guardian** possess the key and can generate valid MACs. It does not prove unique Gateway authorship, independent fixture freshness or external server behavior. `control/presentBasis` is **test instrumentation, not ACS v0.1.0 wire authorization**; do not invent a normative ACS digest field. Guardian response authentication/request binding is also a pre-freeze design requirement, not a benefit automatically provided by a basis MAC.

**Reference ACK/permit finding:** a `steps/toolCallResult` sent as a `dispatched` report can return `allow / result recorded` while the reservation becomes `HELD`. This is **an ACK, not permission**. ### F2 proposed basis authentication, time and restart profile

The complete basis envelope includes all §3 provenance, definition artifact/hash references, `capture_stage`, `case_id`, `run_id`, `operation_id`, `attempt_id`, source revision/sequence, `audience`, `issued_at`, nonce, schema/version, `key_id` and declared algorithm. `definition_source` is its **only normative source-mode field**. The proposed `signature` is lower-hex HMAC-SHA256 of UTF-8 RFC 8785 JCS bytes of the entire object after removing that one field; reject duplicate/unknown forbidden fields and nonconforming schemas. Pin the exact audience/issuer identifiers, timestamp serialization and schema before freeze; no abbreviated §7 example is a complete authenticated envelope.

Gateway measures/authenticates; Guardian verifies using the orchestrator-generated random **32-byte** per-run key, with read-only secret mounts in **Gateway and Guardian only**, `key_id=run_id`. No environment-variable, log, evidence or receipt export of key material. Destroy it at run closure. HMAC shared-key verification is not asymmetric issuer attribution. Key loss or unverified mount/identity after restart means no new permit; reconciliation/readback must remain possible without recovering a key from logs.

**Proposed time policy for sign-off:** use the trusted orchestration host's UTC clock, synchronized before case start, with Gateway/Guardian verified offset bounded by **1 second**; record synchronization/health evidence, not just claimed timestamps. Maximum accepted basis age is **30 seconds**, including skew uncertainty: require `max(0, verifier_now - issued_at) + 1 second <= 30 seconds` and reject an issuance time more than 1 second in the future. The one-second tolerance, time source identity and exact UTC serialization are **integrator proposals awaiting scoped F2 acceptance**, not decisions attributed to Malachi.

**Durable replay/fencing policy:** Guardian atomically validates basis/identity/freshness and durably records accepted `(run_id, attempt_id)` and nonce/decision binding before returning a usable decision. Attempt IDs are unique across A1/R1 and retries; duplicates cannot become fresh requests. Persist the permit's at-most-once consumption and Gateway send-intent/fencing state across crashes; if this state is missing or unreconciled, withhold a send. Capture replay rejection separately from permit reuse. Authentication/freshness/identity failure maps to `basis_not_presented` with a precise subreason; unavailable replay storage is also fail-closed. Exact storage/transaction semantics and authenticated Guardian reply channel remain pre-freeze design decisions.

**Verification versus key destruction:** retain raw/canonical envelopes and MACs plus separately authenticated verifier/Guardian validation records, never the run key. Before key destruction, perform declared in-boundary MAC verification and bind its result to immutable records; post-run offline reviewers can rehash artifacts and verify independently authenticated issuer records/public signatures. The exact protected verification interface/attestation trust and sequencing must be approved under F1/F2/F5; do not claim full independent offline MAC recomputation unless an explicitly reviewed compatible mechanism actually provides it.

The fixture pins D0 throughout C0 and holds D1 stable after activation until C2/C3 closure. Conversion and forwarding use the exact immutable snapshot measured for that attempt; basis authentication does not itself enforce this binding.

Every actual run must preserve original raw bytes (A1, R1, ACS request and response, actual ERP payload), JCS bytes/digest, source revision and source permissions, Gateway forward/no-forward observations, and independent post-409/timeout readback. The absence of a suitable trusted source or an honest pre-forward mapping is `NOT_RUN / DESIGN_BLOCKED`, not a reason to fabricate a `dispatched` event.
